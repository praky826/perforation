Phase 7 Completion Summary: Pipeline Orchestration & Version Stamping

Note: Both files for this phase (runner.py and version_stamp.py) already existed on disk, timestamped during a prior working session but never summarized or confirmed. This summary was authored after reading both files in full, cross-referencing every step call against the actual run_stepNN signatures extracted from the 23 step modules, byte-compiling, importing, and verifying zero real Qt imports. All 23 pipeline step files exist, so building runner.py is permitted under the development-order rule.

Files Reviewed and Purpose:
backend/pipeline/runner.py implements the PipelineRunner class, the single execution engine for the 23-step pipeline. It holds the fixed STEP_PHASE mapping (step 1 to phase 0; 2-5 phase 1; 6-10 phase 2; 11-18 phase 3; 19-23 phase 4) and PHASE_NAMES, threads each step's in-memory output to the next through a ctx dict, emits progress events, writes manifest status transitions for crash recovery, and supports resume/reprocess from an arbitrary stage by rebuilding context from persisted outputs.
backend/reporting/version_stamp.py captures the version-metadata block (app_version 1.0.0, python_version, config_snapshot from get_pipeline_constants_dict, library_versions of the 11 confirmed-stack distributions via importlib.metadata, captured_at) and writes it once into manifest.version_metadata via stamp_session. It reads PySide6's version by name without importing Qt, preserving the backend boundary.

Key Functions and Signatures:
PipelineRunner(session_manager=None). run(session_id, start_step=1, progress_callback=None) -> dict returning {status: complete, last_step: 23} or {status: failed, failed_step, error}. reprocess_from_stage(session_id, start_step, progress_callback=None) -> dict which calls manifest.invalidate_from_stage(start_step) then run. Internal _execute_step(step_id, ctx) dispatches each step; _rebuild_context reconstructs ctx from disk for resume; loaders reconstruct CalibrationRecord, StampFrame, HoleRecord list, registered frames, crops, outlines, profiles, tables, composites, scores, and flags. version_stamp: get_library_versions() -> dict, build_version_metadata() -> dict, stamp_session(session_id, session_manager=None) -> dict.

Data Flow and Progress Events:
On a fresh run (start_step 1) stamp_session writes version metadata first. Each step is bracketed by progress events {step_id, phase, phase_name, status} where status is started, complete, or failed; a failed step also carries detail. The same transitions are mirrored into manifest (add_stage_entry with status failed, set_status). holes_total and holes_processed are set inside step 8 and step 18 respectively (not by the runner), and Feature 7 reads them from the manifest. Step 23 uses ctx frames diffuse brightness_array (already orientation-normalized by step 6) as the overview image. On any step exception the runner logs, writes a failed stage entry, sets status failed, emits the failed event, and returns without raising, leaving prior outputs intact.

Ambiguities Encountered and Resolution:
The algorithm document assumes every step can resume purely from persisted disk outputs, but steps 1-6 pass in-memory float frames that are only persisted as 8-bit registered PNGs. For image-dependent resume points (steps 7-16 and 23) the runner reloads those PNGs and re-applies the persisted rotation angle from StampFrame; this is a documented precision caveat to be validated against real capture data, not a spec deviation. ReferenceGroup is recomputed on resume via build_reference_groups since it is a pure function of edge assignments and is not persisted separately.

Decisions Made Not Explicitly in Documents:
The progress channel is a caller-supplied callback rather than a global event bus, so the frontend can subscribe without the backend importing any UI code; a callback that raises is caught and ignored so a UI fault never breaks the pipeline. _working_crops prefers focus-fused crops (step 10) when present, else raw crops (step 9), matching the algorithm note that fusion is optional. PHASE_NAMES strings are runner-local display labels.
