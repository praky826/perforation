How to Read This Document
This document specifies the backend half only of the 29 usability features defined in USABILITY_FEATURES_AND_TECH_STACK.docx. Frontend widgets (PySide6 tabs, dialogs, plots) are named only as the consumer of each feature's backend output — their internal implementation is out of scope here. Every feature's backend logic is reached exclusively through backend/api.py, the one module the frontend package is allowed to import from (per IPDS_Project_File_Structure.docx).
A large share of these features (Categories C, D, E) do not introduce new computation at all — their entire backend job is to query, aggregate, or format outputs that the pipeline in Document 1 already produced. Where that is the case, this document says so explicitly rather than inventing new algorithms for numbers the pipeline has already computed.
Every feature entry follows the same six-part template used in Document 1:
Purpose — why the feature exists and which risk or usability gap it closes.
What it does (detailed) — the effect of the feature in plain terms.
How it is implemented (detailed) — the specific technique, and, where relevant, which pipeline step's output it reuses.
Dependencies — which pipeline steps or other features feed it, and what consumes it.
Files used — exact paths from the confirmed project file structure.
Algorithm — the step-wise execution flow of its backend logic.
  Shared record shapes referenced below (HoleRecord, DeviationScore, Manifest, etc.) are defined once in Document 1, Appendix A — Data Contracts. This document does not redefine them.

Feature 29

Category A — Capture & Session Setup
Feature 1: Pre-Flight Capture Checklist
  Backend files: backend/config/capture_schema.py, backend/session/session_manager.py, backend/api.py
Purpose
To stop a session from ever reaching the pipeline with a missing or mis-tagged image, since several downstream steps (Step 1 ingestion, Step 3 illumination geometry, Step 7 candidate detection) have no way to recover from a genuinely missing required frame.
What it does (detailed)
On every upload event, compares the session's currently tagged file set against the required-items schema (1 diffuse, 4 torch, 1+ backlit, 1 calibration, optional ball-bearing set) and reports pass/fail per individual item rather than one generic error, enabling or disabling the 'Process' action accordingly.
How it is implemented (detailed)
capture_schema.py holds a plain data structure of {tag, min_count, max_count, required: bool} entries — the same schema Step 1 itself validates against, so the checklist and the ingestion step can never silently disagree about what is required.
session_manager.py maintains the session's current tagged-file set on disk; on each upload event, api.py diffs the current set against the schema and returns a per-tag status list.
'Process' is only enabled once every required-tag entry is satisfied; missing optional items (ball bearing) never block it.
Dependencies
Downstream: Step 1 (Raw Capture Ingestion) reuses the identical capture_schema.py definition, so a session that passes this checklist is guaranteed to pass Step 1's own validation.
Feeds: frontend/tabs/upload_tab.py, which renders the per-item status icons this feature's backend half computes.
Files used
backend/config/capture_schema.py — required-tag schema (shared with Step 1)
backend/session/session_manager.py — tracks the session's current uploaded/tagged files
backend/api.py — exposes the checklist result to the frontend
Algorithm (step-wise execution flow)
On each upload event, read the current list of tagged files for the session from session_manager.py.
Load the required-items schema from capture_schema.py.
For each schema entry, count how many uploaded files carry that tag and compare against min_count/max_count.
Build a per-tag status list: Pass, Fail (missing), or Fail (duplicate/over max).
Compute overall readiness = true only if every required (non-optional) entry status is Pass.
Return the per-tag status list and overall readiness via api.py to the frontend checklist widget.
Feature 2: Structured Session Log Form (with Live Elevation Calculation)
  Backend files: backend/session/session_manager.py, backend/api.py (numpy trig calculation)
Purpose
To capture the hand-measured rig geometry as structured, machine-readable fields — the same numbers Step 3 (Illumination Geometry Determination) needs — and to surface the exact same elevation formula Step 3 uses at data-entry time, so a bad measurement is visible immediately rather than after the whole pipeline has run.
What it does (detailed)
As the user enters height/distance/correction for a torch, computes elevation = arctan(height/distance) + correction live and returns it for display, and on save, writes all four torches' final values into the session's SessionLog record.
How it is implemented (detailed)
The live-calculation endpoint is a stateless numpy computation — it mirrors Step 3 Path A's formula exactly, so what the user sees while typing is guaranteed to match what the pipeline will later compute, not an approximation of it.
A warning (not a block) is returned whenever the calculated elevation falls outside the 15-20 degree recommended range from the hardware protocol, consistent with that range being a starting point rather than a hard law.
On save, the full 4-torch SessionLog record plus camera_settings is written to session_log.json via session_manager.py, in the exact schema Step 1 expects to read.
Dependencies
Downstream: Step 1 reads the resulting session_log.json; Step 3 Path A reuses the identical elevation formula computed here.
Feeds: frontend/tabs/session_log_tab.py.
Files used
backend/api.py — compute_elevation(height_cm, distance_cm, correction_deg) live endpoint; save_session_log(session_id, log_data)
backend/session/session_manager.py — persists the finalized SessionLog
data/sessions/<session_id>/session_log.json — output
Algorithm (step-wise execution flow)
On each keystroke/change event for a torch's height, distance, or correction field, call compute_elevation with the current values.
Compute elevation_deg = arctan(height_cm / distance_cm) + correction_deg (default 0).
Check elevation_deg against the 15-20 degree recommended band; set a warning flag if outside it, without blocking entry.
Return elevation_deg and the warning flag for immediate display.
On explicit save, validate that all 4 torches have azimuth/height/distance values and camera_settings is fully populated.
Write the completed SessionLog to session_log.json via session_manager.py.
Confirm the write succeeded back to the frontend form.
Feature 3: Shadow-Bleed Check Reminder
  Backend: state only, via backend/session/session_manager.py
Purpose
To make the hardware protocol's manual shadow-bleed verification (Hardware doc, Step C2) an explicit, recorded gate before capture proceeds, since a missed shadow-bleed check would silently corrupt every hole's Step 17 directional descriptor with cross-talk from its neighbor.
What it does (detailed)
Displays the shadow-bleed check as a required checklist item before a session is marked ready to capture, and records the user's boolean acknowledgment against the session.
How it is implemented (detailed)
This feature has no computation — it is a static procedural gate. The only backend behavior is persisting a single boolean field against the session record, and refusing to mark the session 'ready to capture' until that field is true.
Dependencies
Precedes: Feature 1's checklist and, ultimately, Step 1 ingestion — a session cannot be marked ready without this acknowledgment on record.
Feeds: frontend checklist item component.
Files used
backend/session/session_manager.py — stores the shadow_bleed_acknowledged boolean
backend/api.py — acknowledge_shadow_bleed_check(session_id)
Algorithm (step-wise execution flow)
Present the shadow-bleed reminder as a checklist item when the session enters its 'ready to capture' stage.
On user confirmation, call acknowledge_shadow_bleed_check(session_id).
Set shadow_bleed_acknowledged = true on the session record via session_manager.py.
Allow the session to proceed to the capture-ready state only once this flag is true (in addition to Feature 1's checklist).
Feature 4: Brightness-Mismatch Warning
  Backend: reuses Step 4 output; backend/api.py
Purpose
To surface a torch hardware problem (dying battery, misplaced torch, ambient light leak) as soon as it is detectable, rather than letting it silently degrade Step 17's directional fit.
What it does (detailed)
After Step 4 computes each torch's brightness correction factor, compares it against a tolerance band around 1.0 and visually flags any torch whose factor falls outside that band.
How it is implemented (detailed)
Performs no new computation — it is a threshold check on Step 4's existing output. The tolerance band (e.g. ±0.15) is a named constant in pipeline_constants.py so it stays consistent with, and auditable alongside, every other pipeline threshold.
Dependencies
Upstream: Step 4 (Brightness-Matching) produces the 4 correction factors this feature reads directly, with no recomputation.
Feeds: session summary display in frontend/tabs/session_log_tab.py or processing_tab.py.
Files used
data/sessions/<session_id>/stages/brightness_correction.json — Step 4's output, read here
backend/config/pipeline_constants.py — the ±0.15 tolerance band constant
backend/api.py — get_brightness_warnings(session_id)
Algorithm (step-wise execution flow)
Read the 4 correction factors from brightness_correction.json once Step 4 has completed.
Read the tolerance band constant from pipeline_constants.py.
For each torch's factor, check whether it falls outside [1 - tolerance, 1 + tolerance].
Build a per-torch warning list: {torch_index, factor, warning: bool}.
Return the list via get_brightness_warnings for display as a badge per torch.
Category B — Processing Transparency
Feature 5: Stage-by-Stage Progress Indicator
  Backend file: backend/pipeline/runner.py
Purpose
To show which of the pipeline's five phases is currently executing, by name, so a multi-minute run does not look like a frozen generic spinner.
What it does (detailed)
Emits a stage-change event each time the pipeline runner transitions between the 23 constituent steps (and, by extension, the 5 phases), which the frontend subscribes to and renders as a labeled progress stepper.
How it is implemented (detailed)
runner.py maintains a static step-number-to-phase-name mapping and calls a progress callback immediately before and after each step function executes.
The callback payload is {step_id, phase_name, status: 'started'|'complete'|'failed'}; api.py exposes this as a pollable status endpoint (or a push stream, if the frontend transport supports one).
Dependencies
Wraps: all 23 pipeline steps (Steps 1-23) — runner.py is the single execution entry point for the whole Phase 0-4 pipeline.
Feeds: Feature 7 shares the same event channel for its per-hole counter; frontend/tabs/processing_tab.py.
Files used
backend/pipeline/runner.py — stage-addressable execution and progress events
backend/api.py — get_pipeline_status(session_id)
backend/session/manifest.py — status also persisted here for crash-resume (Feature 22)
Algorithm (step-wise execution flow)
runner.py holds the ordered list of the 23 step functions grouped into their 5 phases.
Before invoking each step function, emit a 'started' event with {step_id, phase_name}.
Execute the step function.
After it returns, emit a 'complete' event (or 'failed', with the exception detail, if it raised).
Write the same status transition into manifest.json so a page reload or crash-resume sees an accurate current stage.
api.py's get_pipeline_status reads the latest event/manifest state for the frontend to render as a labeled stepper.
Feature 6: Live Thumbnail Preview Per Stage
  Backend file: backend/session/manifest.py
Purpose
To let the user see a stage's actual output image as soon as it is ready, rather than waiting for the entire 23-step run to finish before anything is visible.
What it does (detailed)
As each pipeline step writes its output image to disk, appends an entry to manifest.json immediately; the frontend polls or watches the manifest and appends a new thumbnail to a live strip as entries arrive.
How it is implemented (detailed)
Every step in Steps 1-23 that produces a displayable image (e.g. Step 5's registered frames, Step 6's boundary overlay, Step 23's annotated overview) calls manifest.py's append-entry function immediately on writing that file, tagging the entry with stage, hole_id (if applicable), edge (if applicable), and flagged (once Step 21 has run).
manifest.py treats manifest.json as an append-mostly log rather than something rewritten wholesale each time, so a crash mid-session leaves a valid partial record (also what Feature 22 relies on).
Dependencies
Upstream: every stage-producing step across all 5 phases.
Downstream: Feature 10 (filter/group) reads the same tagged entries; Feature 22 (crash resume) reads manifest.json as its single source of truth.
Feeds: frontend/widgets/thumbnail_strip.py.
Files used
backend/session/manifest.py — read/write logic, single source of truth
data/sessions/<session_id>/manifest.json
backend/api.py — get_manifest_diff(session_id, since_token) for incremental polling
Algorithm (step-wise execution flow)
Each producing step, immediately after writing its output image to disk, calls manifest.py's append function with {path, stage, hole_id, edge, flagged}.
manifest.py appends the entry to the images array in manifest.json and updates the file's modification token.
The frontend calls get_manifest_diff periodically (or on a file-watch signal) passing the last token it saw.
get_manifest_diff returns only entries added since that token.
The frontend appends the new entries to the live thumbnail strip without re-fetching the whole manifest.
Feature 7: Per-Hole Progress Counter
  Backend file: backend/pipeline/runner.py
Purpose
To give a concrete sense of progress during Phase 3 (Steps 11-18), which is the slowest phase since it runs independently for every hole on the specimen.
What it does (detailed)
Shows a live 'Hole N/Total processed' counter by tracking how many holes have completed the full per-hole feature-extraction sequence (Steps 11 through 18).
How it is implemented (detailed)
runner.py sets total_holes once Step 8's classification completes (this is the first point the true count is known), and increments holes_processed each time a given hole finishes Step 18 (Composite Signature Assembly), since that is the last step in the per-hole sequence.
Emits this as a progress event on the same channel Feature 5 uses, so the frontend can drive both the phase stepper and the per-hole counter from one subscription.
Dependencies
Upstream: Step 8 (for total_holes) and Step 18 (for each increment).
Shares: the same event channel and manifest fields as Feature 5.
Feeds: frontend/tabs/processing_tab.py.
Files used
backend/pipeline/runner.py — holes_processed / total_holes counter state
backend/session/manifest.py — holes_total and holes_processed fields
backend/api.py — get_hole_progress(session_id)
Algorithm (step-wise execution flow)
When Step 8 completes, read the final hole count and set manifest.holes_total to it.
As Phase 3 runs (potentially in parallel across holes, per Step 9's design intent), each time a hole completes Step 18, increment manifest.holes_processed by 1.
Emit a progress event {holes_processed, holes_total} on the same channel as Feature 5's stage events.
get_hole_progress returns the current counts for the frontend's progress text/bar.
Category C — View Tab
Feature 8: Side-by-Side / Overlay Comparison Toggle
  Backend: no new computation; backend/api.py
Purpose
To let the user directly compare a 'before' and 'after' image (e.g. raw backlit vs. contour overlay) without any extra alignment work, since Step 5 has already guaranteed every session image shares one pixel coordinate system.
What it does (detailed)
Given two selected manifest entries, returns their file references for the frontend to render either side-by-side or as an alpha-blended overlay; performs no re-alignment, since none is needed.
How it is implemented (detailed)
Purely a manifest lookup: given two image identifiers, api.py resolves them to file paths already known to be co-registered from Step 5, and returns both paths plus their tags for the frontend's QGraphicsView compositing.
The alpha-blend slider and side-by-side split are entirely a frontend rendering concern; the backend contributes only the guarantee of shared coordinates and the resolved file paths.
Dependencies
Upstream: Step 5 (Cross-Pass Image Registration) is what makes this feature valid without extra work.
Feeds: frontend/tabs/view_tab.py.
Files used
backend/session/manifest.py — resolves image identifiers to file paths
backend/api.py — get_comparison_pair(session_id, image_id_a, image_id_b)
Algorithm (step-wise execution flow)
Receive two manifest image identifiers from the frontend selection.
Look up both entries in manifest.json via manifest.py.
Confirm both entries belong to the same registered coordinate frame (i.e. both post-date Step 5).
Return both resolved file paths and tags to the frontend for it to render as side-by-side panes or an alpha-blended overlay.
Feature 9: Synchronized Zoom/Pan
  No dedicated backend file — pure frontend transform-mirroring, resting on Step 5's registration guarantee
Purpose
To keep the zoom and pan position identical across two compared image panes, which is only physically meaningful because both panes share one coordinate frame.
What it does (detailed)
Mirrors zoom/pan transforms from one image pane onto the other, since Step 5 already guarantees they share a coordinate system — no per-interaction backend call is involved.
How it is implemented (detailed)
This is entirely a frontend widget-linkage behavior (binding two QGraphicsView transformation matrices via a shared signal/slot connection); there is no backend computation to specify.
It is included here for completeness because the feature would be meaningless without the backend guarantee it depends on: if Step 5's registration were ever imprecise, a synchronized zoom/pan would visibly reveal that misalignment rather than mask it.
Dependencies
Upstream: Step 5 (Cross-Pass Image Registration) is the sole backend dependency — it is what makes 'the same pixel = the same physical point' true across the two panes being synchronized.
Feeds: frontend/widgets/graphics_view_sync.py entirely.
Files used
(none — frontend-only; relies on Step 5's already-registered output, no additional backend file)
Algorithm (step-wise execution flow)
(No backend algorithm.) The registration guarantee this feature depends on is produced once, upstream, by Step 5; from that point on this feature is pure frontend state-mirroring with no further backend involvement.
Feature 10: Filter/Group Controls (View Tab)
  Backend: manifest tagging fields (shared with Feature 6); backend/api.py
Purpose
To let the user narrow a potentially large image gallery down to what they actually want to look at — one stage, one hole, one edge, or only flagged holes — without scanning the whole session.
What it does (detailed)
Applies a filter predicate (stage / hole_id / edge / flagged-only) over the manifest's tagged image entries and returns only the matching subset.
How it is implemented (detailed)
Reuses the same stage/hole_id/edge/flagged tagging fields Feature 6 already requires on every manifest entry — no additional tagging work is needed, only a query function over data that already exists.
The filter is a straightforward predicate function evaluated server-side (so large sessions don't need their full manifest shipped to the frontend just to be filtered client-side).
Dependencies
Upstream: Feature 6's manifest tagging fields; ultimately every stage-producing step across Phases 0-4 that writes those tags.
Feeds: frontend/tabs/view_tab.py.
Files used
backend/session/manifest.py — the tagged images array
backend/api.py — query_gallery(session_id, filters)
Algorithm (step-wise execution flow)
Receive a filter specification {stage?, hole_id?, edge?, flagged_only?} from the frontend.
Load the manifest's images array via manifest.py.
Apply each provided filter condition as a predicate over the array (all provided conditions are ANDed together).
Return the filtered subset of image entries to the frontend for re-rendering the gallery.

Category D — Math Explanation & Traceability
Feature 12: Per-Hole "Why Flagged" Breakdown Panel
  Backend: exposes Step 20's per-descriptor intermediate values; backend/api.py
Purpose
To let the user see exactly which signal — shape, roughness, or shadow — actually drove a hole's outlier flag, rather than only a single opaque combined score.
What it does (detailed)
For a selected hole, returns a table of {descriptor name, hole value, group median, group MAD, robust z-score} for every field in the composite vector, plus which field(s) exceeded the outlier threshold, and a description of the comparison group used (edge-based or pooled, with low_confidence noted).
How it is implemented (detailed)
Pulls per-descriptor median/MAD/z-score values already computed and stored by Step 20 — this feature performs no new statistics, only formatting and highlighting of existing DeviationScore fields.
Sorts/highlights rows by |z-score| so the most discriminating descriptor(s) are visually prominent.
Reads Step 19's stratification and low_confidence fields to render the comparison-group description text.
Dependencies
Upstream: Step 20 (DeviationScore per_field_z/group_median/group_mad), Step 19 (ReferenceGroup stratification), Step 18 (field_names for labeling).
Feeds: frontend/widgets/breakdown_table.py and frontend/tabs/results_tab.py.
Files used
data/sessions/<session_id>/holes/<hole_id>/score.json — source DeviationScore
backend/api.py — get_hole_breakdown(session_id, hole_id)
Algorithm (step-wise execution flow)
Load the hole's score.json (DeviationScore) and its CompositeSignature.field_names.
Zip field_names with per_field_z, group_median, and group_mad into one row per descriptor field.
Sort rows by descending |z-score|.
Mark rows whose |z-score| exceeds the field-level notability threshold (e.g. matching the overall cutoff's per-field equivalent) as 'driver' rows.
Read the hole's ReferenceGroup stratification and low_confidence flag from Step 19's output.
Return the row table plus the comparison-group description text via get_hole_breakdown.
Feature 13: Pairwise Hole Comparison View
  Backend: extends Step 20's group logic with an in-group centrality ranking; backend/api.py
Purpose
To let the user see a flagged hole directly next to a concrete, typical example from its own comparison group, rather than only an abstract statistical summary.
What it does (detailed)
By default, identifies the comparison group's most 'typical' hole (the one with the smallest combined deviation from the group's own median) and returns both holes' descriptor tables, deltas, and matching image crops; supports a manual override to compare against any other hole in the session.
How it is implemented (detailed)
Auto-selection reuses Step 20's own scoring logic, but applied to rank the comparison group's members against their own group median (rather than testing the held-out hole) — the minimum-scoring member is the 'most typical' hole.
Manual override simply substitutes a user-chosen hole_id in place of the auto-selected one; the rest of the comparison (delta table, crops) is identical either way.
Dependencies
Upstream: Step 19 (ReferenceGroup), Step 20 (scoring logic reused for centrality), Step 9 (crops for both holes).
Feeds: frontend/tabs/results_tab.py's dual-pane layout.
Files used
data/sessions/<session_id>/holes/<hole_id>/score.json and descriptors.json — for both holes being compared
backend/api.py — get_pairwise_comparison(session_id, hole_id, compare_to=None)
Algorithm (step-wise execution flow)
Load the target hole's ReferenceGroup (comparison_group_ids) from Step 19.
If compare_to is not supplied: for each member of comparison_group_ids, compute its own combined deviation score against the group median (reusing Step 20's scoring function) and select the minimum-scoring member as the reference hole.
If compare_to is supplied: use that hole_id directly as the reference hole, skipping the ranking step.
Load both holes' CompositeSignature and DeviationScore, and compute a per-field delta between them.
Load both holes' matching crops (Step 9 output) for the paired image display.
Return the descriptor tables, deltas, and crop references via get_pairwise_comparison.
Feature 14: Shadow-Direction Vector Diagram
  Backend: reuses Step 17 output directly; backend/api.py
Purpose
To make directional inconsistency across a set of holes visible at a glance, rather than requiring the user to compare shadow-direction numbers row by row.
What it does (detailed)
For a given set of holes (typically one edge), returns each hole's shadow strength and direction (Step 17's output) formatted for a compass-style vector plot, one arrow per hole, optionally including each hole's outlier flag for color-coding.
How it is implemented (detailed)
No new computation: strictly reads strength and direction_deg from each hole's ShadowDescriptor, plus is_outlier from OutlierFlag if the color-code option is requested.
Grouping (typically by edge) is done using Step 8's edge tag, matching the ordering used everywhere else in the pipeline.
Dependencies
Upstream: Step 17 (ShadowDescriptor), Step 21 (OutlierFlag, optional), Step 8 (edge grouping).
Feeds: frontend/widgets/compass_plot.py.
Files used
data/sessions/<session_id>/holes/<hole_id>/descriptors.json (field: shadow) — source
backend/api.py — get_shadow_vectors(session_id, edge=None)
Algorithm (step-wise execution flow)
Receive an optional edge filter.
Select all holes matching that edge (or all holes, if no filter given).
For each selected hole, read strength and direction_deg from its ShadowDescriptor, and is_outlier from its OutlierFlag.
Assemble a list of {hole_id, strength, direction_deg, is_outlier} entries.
Return the list via get_shadow_vectors for the frontend's Matplotlib polar-plot rendering.
Feature 15: "Show the Math" Expandable Explanation Blocks
  Backend: template population from existing Step 13/15/17/20 values; backend/api.py
Purpose
To make the pipeline's statistics legible to a non-technical examiner, by populating the actual formula with that specific hole's real numbers rather than presenting the statistics as an unexplained black box.
What it does (detailed)
For a selected hole, populates one text template per descriptor category (shape, roughness, shadow) with that hole's real computed numbers and a one-line plain-language interpretation, generated live rather than pre-written.
How it is implemented (detailed)
Defines one template string per descriptor type with placeholders for hole value, group median, group MAD, and z-score (e.g. "GLCM contrast: {value} vs. group median {median}, MAD {mad} -> robust z = {z}"), stored as simple Python format strings, not new computation.
Populates each template at request time directly from the hole's already-computed Step 13/15/17 descriptor values and Step 20's DeviationScore — this is purely a text-rendering pass over existing numbers.
Dependencies
Upstream: Step 13, Step 15, Step 17 (descriptor values), Step 20 (z-scores).
Feeds: frontend/widgets/math_block.py's collapsible panels.
Files used
data/sessions/<session_id>/holes/<hole_id>/descriptors.json and score.json — source values
backend/api.py — get_math_explanation(session_id, hole_id)
Algorithm (step-wise execution flow)
Load the hole's ShapeDescriptor, RoughnessDescriptor, ShadowDescriptor, and DeviationScore.
For each descriptor category, select its template string and the specific fields it references.
Substitute the hole's actual values, the matching group_median/group_mad from DeviationScore, and the corresponding per_field_z into the template.
Append a one-line plain-language interpretation derived from whether that category's z-score(s) exceed the notability threshold.

Feature 29: Input-Quality Gating
  Backend: lightweight pre-processing checks reusing Steps 2, 4, 7 logic; backend/api.py
Purpose
To catch a capture-quality problem (poor backlit contrast, inconsistent torch exposure, an undetectable calibration target) before the full pipeline runs on data that was never going to produce trustworthy descriptors.
What it does (detailed)
Before the full pipeline runs, checks whether the backlit image shows the expected bimodal (bright hole / dark paper) brightness distribution, whether the four torch images have comparable overall exposure, and whether the calibration target is detectable at all — blocking on failure, warning (with required acknowledgment) on marginal results.
How it is implemented (detailed)
Backlit check: computes the image histogram and evaluates bimodal separation quality via an Otsu-threshold variance check, reusing the same thresholding approach Step 7 will later apply, but as a lightweight quality gate rather than the full candidate-detection pass.
Torch exposure check: compares mean brightness across the four raw torch images within a tolerance band, conceptually the same comparison Step 4 performs, run here early and cheaply before the full brightness-matching pipeline stage.
Calibration check: attempts Step 2's pattern-detection early, on the raw calibration frame, and fails the gate outright if the pattern cannot be found at all (since nothing downstream can proceed without it).
Dependencies
Reuses logic from: Step 2 (pattern detection), Step 4 (torch exposure comparison), Step 7 (bimodal threshold quality) — as lightweight pre-checks, not full executions of those steps.

backend/api.py — run_quality_gate(session_id)
Algorithm (step-wise execution flow)
Load the raw backlit, four raw torch, and raw calibration frames (before full Step 1-5 processing).
Compute the backlit frame's brightness histogram and evaluate its Otsu-threshold separation quality; fail if the distribution is not sufficiently bimodal.
